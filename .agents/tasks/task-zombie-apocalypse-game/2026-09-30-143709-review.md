# Zombie apocalypse vertical slice — cure storyline, two zones, procedural assets (v1)

A single-player three.js game realizing the "wake in Odisha → fight through the zombie city → knife-to-gun progression → survivors + research center → collect cure ingredients → travel north to the Medical Facility → deliver → helicopter finale → WIN" loop, with player death → LOSE. Everything is built offline from `AssetFactory` primitives (no external assets), audio is procedural Web Audio, and the whole story is exposed to a headless harness through `window.__GAME__.test`. The state machine (START/PLAYING/PAUSED/WIN/LOSE), combat (knife cone + gun hitscan), NPCs (friendly/hostile/scientist, all killable), zone travel with an ingredient gate, and a soft-lock-proof delivery fallback are all present and, where reachable, work correctly.

Watch for: **the quest is soft-locked at the very first objective in normal play — nothing advances `OBJ_WAKE` → `OBJ_SURVIVE`, so zombie kills never count and the entire story is unreachable without the test hooks (confirmed).** The event-driven flow is otherwise wired end-to-end and completes cleanly once that first transition is bypassed. Secondary: the test hooks force-advance the quest with `advanceTo(..., silent)`, which masks the `OBJ_WAKE` gap during automated verification (confirmed); zones are never GPU-disposed on unload/restart (likely leak); and `QuestManager` has no instance `requiredIngredients`, so `Game` reads `undefined` and silently falls back to 3 (confirmed).

**Verdict**: NEEDS_CHANGES

## High-level view

The story is a fixed ordered objective list in `QuestManager`, advanced by `handleEvent` calls the zones and `Game` fire (kills, pickups, talk, enter-research, travel, deliver, board). Every transition past the opening is correctly wired and verified to complete the game — except the first one: `OBJ_WAKE` has no completion condition anywhere in the code, and `zombie_killed` only counts while the objective is already `OBJ_SURVIVE`. So a real player who starts, leaves the room, and kills zombies stays on `OBJ_WAKE` forever with `kills` climbing but the objective frozen.

The headless test hooks (`triggerWin`, `collectAllIngredients`, `_forceWin`) drive the quest with `advanceTo(id, {silent:true})`, stepping straight over the missing `OBJ_WAKE` transition. That means automated verification of the "full win path" passes while the human-facing path is broken — the hooks are exercising a different route than a player takes at exactly the one broken step.

Combat, weapon progression, NPC behavior, the ingredient-gated north exit, and the anti-soft-lock terminal fallback (deliver via lab console if the scientist is killed) are all real logic and behave correctly under test. NPC deaths never soft-lock the quest, which matches the design intent and the user's "all NPCs killable" ask.

Resource lifecycle is the other gap: `Zone.unload` only detaches the group from the scene and nothing calls `dispose()` on geometries/materials/textures. Each `_restart()` rebuilds both zones from scratch, orphaning the previous GPU resources. Low impact given only two zones and infrequent restarts, but it accumulates.

<summary>Issues (5)</summary>

1. **OBJ_WAKE soft-lock (blocking)** — Nothing advances `OBJ_WAKE` → `OBJ_SURVIVE`, and `zombie_killed` only counts during `OBJ_SURVIVE`, so normal play is stuck on objective 1 forever. Add a completion trigger: either advance on the first `zombie_killed` (also counting it), or detect the player leaving the room / entering the street and fire the transition. Update the README's "Leave it and step into the city" line to match whatever trigger is chosen.
2. **Test hooks mask the soft-lock** — `triggerWin`/`_forceWin`/`collectAllIngredients` use `advanceTo(..., silent)` to jump past `OBJ_WAKE`, so the harness reports a full win while the player path is broken. After fixing #1, drive the win path through the same event that unblocks `OBJ_WAKE` so the hook exercises real logic, or add an explicit assertion that `OBJ_WAKE` advances via a game event.
3. **Zones never GPU-disposed** — `Zone.unload` only does `scene.remove(group)`; no geometry/material/texture disposal, and `_restart()` rebuilds both zones, orphaning the old ones. Add a `dispose()` that traverses the group and disposes geometries/materials (and cached `AssetFactory` textures if any), called from `unload`/`_restart`.
4. **`requiredIngredients` reads undefined** — `Game._collectAllIngredients` reads `q.requiredIngredients`, which `QuestManager` never sets as an instance field; it only works because of a `? : 3` fallback. Set `this.requiredIngredients = REQUIRED_INGREDIENTS` in the manager (or import the constant in `Game`) so the source of truth isn't duplicated by accident.
5. **Error filter can swallow regressions** — the `main.js` benign-pattern filter drops any error matching `/Pointer Lock/i`, so a future failure surfacing through a pointer-lock path would be hidden from the harness. Keep the pattern list tight and revisit it when pointer-lock handling changes.

### The cure flow is complete except for its first step

`QuestManager` is a clean ordered list: `OBJ_WAKE → OBJ_SURVIVE → OBJ_FIND_GUN → OBJ_MEET_SURVIVORS → OBJ_RESEARCH → OBJ_COLLECT → OBJ_TRAVEL → OBJ_DELIVER → OBJ_FINALE → WIN`, each advanced by a matching `handleEvent` case gated on the current objective id. Driving the events by hand from `OBJ_SURVIVE` onward walks the game all the way to `WIN` with no errors, and the zone wiring that fires those events (`onTalkSurvivor`, `onEnterResearch`, `onDeliver`, `onBoardHelicopter`, the ingredient-gated north exit) is correct.

The break is at the top. `OBJ_WAKE`'s text tells the player to "Leave your room and see what happened outside," but nothing detects leaving the room, and there is no `advanceTo('OBJ_SURVIVE')` anywhere in `js/`. `handleEvent('zombie_killed')` increments `kills` unconditionally but only advances `if (id === 'OBJ_SURVIVE')`. So the player can leave the room, kill every zombie in the city, and the objective never moves:

```
start → OBJ_WAKE → (kill 11 zombies) → still OBJ_WAKE, kills=11
```

That output is from the headless harness — after `killAllZombies` twice, `debugState()` reports `kills:11` with `objectiveId:"OBJ_WAKE"`. Because the gun pickup and every later beat are gated on their predecessor objective, the entire story is unreachable in normal play. The README documents the intended trigger ("Leave it and step into the city"), so this is a missing implementation, not an intentional design choice. Simplest fix that matches both the text and the survive objective: advance `OBJ_WAKE → OBJ_SURVIVE` on the first zombie kill (and count that kill), or add a room-exit detection that fires the transition when the player crosses the doorway.

### Test hooks route around the one broken transition

`_installTestHooks` exposes real logic for most actions — `attack` runs the actual `player.attack`/`_afterHits`, `killAllZombies` deals real damage and fires real `zombie_killed` events, `giveGun` grants the real weapon. But the story-completion hooks lean on `advanceTo(id, {silent:true})`: `_collectAllIngredients` calls `advanceTo('OBJ_FIND_GUN')` and `advanceTo('OBJ_RESEARCH')`, and `_forceWin` calls `advanceTo('OBJ_TRAVEL')` and `advanceTo('WIN')`. `advanceTo` jumps the index directly, so it sails past `OBJ_WAKE` without ever needing the missing transition.

The consequence for this review loop: an automated "does triggerWin reach WIN?" check passes (verified — it does), while the human path is dead on objective 1. The hooks aren't faking the *outcome* (the quest genuinely transitions and `onWin` fires), but they're exercising a code path a player can't reach at the `OBJ_WAKE` step. Once #1 is fixed, the win-path hook should begin from the same event a player triggers so the two paths can't diverge again.

### Killing NPCs never soft-locks — verified

The scientist is `questCritical` with an `onInteract` that delivers, and the Medical Facility also registers a `lab_terminal` interactable whose `action` calls the same `_deliver()`. Killing the scientist (`sci.takeDamage(9999)`) leaves the objective at `OBJ_DELIVER`; interacting with the terminal then advances it to `OBJ_FINALE`, and boarding the helicopter reaches `WIN` — confirmed end-to-end with no console errors. `critical_npc_killed` sets `criticalNpcLost` and surfaces guidance rather than blocking. This satisfies the user's "all NPCs killable" requirement without stranding the player, which is the failure mode most likely to break this kind of quest.

### Zone swap and restart leak GPU resources

There is no `dispose` call in the entire `js/` tree. `Zone.unload(scene)` is just `scene.remove(this.group)` — the group's geometries, materials, and any `AssetFactory` textures stay resident. `Game._restart()` calls `unload`, then `_buildZones()` constructs two brand-new zone instances and rebuilds their meshes, so the previous zones' GPU resources are orphaned every restart, and traveling Odisha→Medical also drops Odisha's resources without freeing them.

Impact is bounded — two small procedural zones, restart is a deliberate user action — so this is not blocking, but it grows unboundedly across repeated restarts in a long session. A `Zone.dispose()` that traverses `this.group` disposing geometries and materials, invoked from `unload` (or at least from `_restart` before rebuilding), closes it. Worth checking whether `AssetFactory` caches shared textures/materials before disposing, to avoid disposing something still in use by the other zone.

### requiredIngredients is read but never set

`_collectAllIngredients` computes `const need = q.requiredIngredients ? q.requiredIngredients : 3`. `QuestManager` exports the `REQUIRED_INGREDIENTS` constant and uses it internally but never assigns `this.requiredIngredients`, so the read is `undefined` (confirmed via `String(window.__GAME__.quest.requiredIngredients)` → `"undefined"`) and the code silently falls back to the hardcoded `3`. It happens to match today, but the duplicated literal will drift if `REQUIRED_INGREDIENTS` ever changes. Set the instance field from the constant, or import the constant into `Game`, so there's a single source of truth.

### Error-capture filter could hide real failures

`main.js`'s benign-pattern filter is scoped narrowly to pointer-lock gesture rejections, which is the right call for headless noise — but it silently drops any future error whose message happens to match `/Pointer Lock/i`, so a regression surfacing through a pointer-lock code path would be swallowed by the harness rather than reported. Keep the pattern list tight and revisit it whenever pointer-lock handling changes. Across every scenario exercised (init, start, combat, full story, scientist-killed fallback, lose, restart) `window.__consoleErrors` stayed empty.
